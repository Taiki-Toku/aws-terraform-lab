CHAPTER 05｜コア構成

Self-HostedとPrivilege Cloud

同じ「CyberArk PAM」でも、自社で金庫を持つか（Self-Hosted）、金庫を預けるか（Privilege Cloud）で、構成も運用も大きく変わります。

この章の全体像

責任分界の違い → Privilege Cloudの構成（ISPSS・コネクタ・Connector Management・Secure Tunnel）→ コネクタ導入の流れ → 比較と選び方

この章のゴール

  • Self-HostedとPrivilege Cloudの責任分界（誰が何を運用するか）を説明できる
  • Privilege Cloudで顧客側に置くもの（コネクタ等）とその役割を説明できる
  • 要件に応じてどちらが向いているかを根拠付きで提案できる
目安 60分前提：第3・4章

1. 責任分界：誰が何を運用するか

自宅の金庫 vs 銀行の貸金庫

Self-Hostedは自宅に金庫を買って置くイメージです。金庫の設置場所・メンテナンス・防犯は全部自分の責任ですが、自由度は最大です。Privilege Cloudは銀行の貸金庫です。金庫室の警備・保守は銀行（CyberArk）が行い、自分は「出し入れの手続き」と「鍵を使う人の管理」に集中できます。ただし銀行の営業ルール（サービス仕様）には従う必要があります。

項目Self-HostedPrivilege Cloud
Vaultの構築・堅牢化・パッチ顧客CyberArk
Vaultのバックアップ・DR顧客CyberArk
Web画面（PVWA相当）顧客（IIS上に構築）CyberArk（SaaSの管理画面）
CPM・PSM・PSM for SSH顧客顧客（コネクタサーバ上で稼働）
ターゲットとの通信顧客ネットワーク内顧客ネットワーク内（コネクタから）
Safe・アカウント・ポリシー設計顧客顧客
利用者・権限・承認の運用顧客顧客
バージョンアップ顧客が計画・実施SaaS部分は自動。コネクタ側は顧客が更新（自動更新の仕組みあり）
SaaSでも「設計と運用」は顧客の仕事

Privilege Cloudにしても、Safe設計・権限・ポリシー・オンボーディング・承認運用は顧客側の仕事のままです。第6章以降の内容は、どちらの形態でも必要な知識です。

2. Privilege Cloudの構成

Privilege Cloudは、CyberArkのSaaS共通基盤であるIdentity Security Platform Shared Services（ISPSS）上で提供されます。ISPSSは認証（Identity）・管理画面・監査などを複数のSaaS製品で共有する土台です。

要素場所役割
Identity（ISPSSの認証基盤）SaaSPrivilege Cloudへのログイン、MFA、社内IdPとのSAML連携
Privilege Cloud（Vault・ポータル）SaaS資格情報の保管、Safe・アカウント・ポリシーの管理、録画の保管・再生
コネクタサーバ顧客側CPM・PSM（Windows）を載せるサーバ。ターゲットに近いネットワークに配置。複数台で冗長化
PSM for SSH顧客側（Linux）SSHセッションの中継・記録（必要な場合）
Connector ManagementSaaS＋顧客側エージェントSaaS画面からコネクタの導入・状態監視・更新を行う仕組み
Secure Tunnel顧客側SaaSとオンプレ間の暗号化トンネル（オンプレADとのLDAP連携等に利用）
Identity Connector顧客側オンプレのADとIdentity（SaaS）をつなぐ
↗

コネクタは「内側から外へ」話しかける。外（SaaS）から社内へ穴を開ける必要は基本的にない。

コネクタからSaaSへのアウトバウンドHTTPS通信が基本です。必要な宛先・ポートはバージョン・リージョンで異なるため、公式の「ネットワーク要件」で必ず確認します。

3. コネクタ導入の流れ

確認ポイント

導入手順・前提条件（OS、.NET、通信要件、トークン有効期限）は更新が頻繁です。必ず最新の「Connector Management」ドキュメントで確認してから作業してください。

4. 比較と選び方

観点Self-Hosted が向くケースPrivilege Cloud が向くケース
ネットワークインターネット接続が許されない閉域環境アウトバウンドHTTPSが許容できる
規制・データ所在資格情報を自社管理下に置くことが規程上必須SaaSの認証・リージョンが要件を満たす
運用体制Vault・DR・バージョンアップを担える体制があるインフラ運用を減らし、設計・活用に注力したい
拡張性既存の高度なカスタマイズ資産があるSIA・SCA・Secrets Hub等のSaaS製品と統合したい
機能追加計画的なバージョンアップで取り込むSaaS部分は継続的に機能追加
移行の相談が増えている

Self-HostedからPrivilege Cloudへの移行案件は増えています。移行では「Safe・アカウント・プラットフォームの移行」「ユーザー認証の切替（LDAP→Identity/SAML）」「録画データの扱い」「並行稼働期間」が主な論点です（ケーススタディ応用編で扱います）。

振り返り問題（第5章）

Q1. Privilege Cloudで、顧客側が運用するものは？

  • Vaultのパッチ適用
  • VaultのDR
  • CPM・PSMを載せたコネクタサーバ
  • SaaSの管理画面のサーバ
Vaultや管理画面はCyberArkが運用し、顧客はコネクタ（CPM・PSM等）を運用します。

Q2. コネクタとSaaS間の通信の基本的な考え方は？

  • コネクタからSaaSへのアウトバウンド通信
  • SaaSから社内へのインバウンド通信をFWで開放
  • 専用線が必須
  • コネクタとSaaSは通信しない
コネクタから外向き（アウトバウンド）に接続するのが基本です。詳細な宛先とポートは公式要件で確認します。

Q3. Privilege Cloudを採用しても、顧客側に残る仕事は？

  • Vaultのハードニング
  • Vaultのバックアップ
  • SaaS管理画面のバージョンアップ
  • Safe設計・権限設計・承認運用
Safe設計や権限・承認の運用は、提供形態に関係なく顧客の仕事です。

Q4. 「インターネット接続が一切許可されない閉域網」の要件に向くのは？

  • Privilege Cloud
  • Self-Hosted
  • どちらも利用不可
  • Secrets Hub
SaaSへのアウトバウンド接続ができない場合はSelf-Hostedが候補になります。
