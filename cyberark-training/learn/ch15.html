1. CyberArk設計の8つの原則

#原則具体的には関連章
1金庫は最も堅牢にVaultは専用・堅牢化・ドメイン非参加。Masterの鍵はオフライン保管4
2見せずに使わせるRetrieveより「Use＋PSM」。パスワードを知る人を増やさない6, 10
3人ではなく仕組みで変えるパスワード変更はCPMで自動化。手作業の変更をなくす8
4最小権限と職務分掌必要な人に必要な権限だけ。管理する人と使う人を分ける6, 9
5経路を一本化するFW等で、ターゲットの管理ポート（RDP/SSH）へはPSM等からのみ接続可能にする。抜け道があると統制も検知も効かない10, 12
6止まらない・止まっても困らない冗長化・DR・バックアップ、そして全停止時の緊急手順（ブレークグラス）4, 11
7常設特権を減らすなくせる特権はZSP/JITでなくし、残るものはVaultで守る14
8標準化と自動化命名規則・プラットフォーム・登録手順を標準化し、APIで自動化する6, 7, 本章
原則5「経路の一本化」は空港の保安検査

空港では、搭乗口へ行くには必ず保安検査場を通ります。保安検査場がどれだけ厳格でも、横に「検査なしで通れる通用口」があれば意味がありません。特権アクセスも同じで、PSMを通らずにサーバへ直接RDP/SSHできる経路が残っていると、統制は抜け道だらけになります。

2. 段階導入（ロードマップ）

CyberArkは、リスクの高いものから順に導入していく段階的なアプローチ（CyberArk Blueprint for Identity Security Success など）を公開しています。考え方の例を示します。

段階目的主な対象・施策（例）
段階1資格情報の窃取を防ぐドメイン管理者などの最重要アカウントをVaultに格納・自動変更・PSM経由に限定。緊急用アカウントの統制
段階2横展開・権限昇格を止めるサーバのローカル管理者、DB・ネットワーク機器の管理者、ワークステーションの権限（EPM）へ拡大
段階3特権の悪用を最小化するアプリのシークレット、クラウド、ZSP/JITの適用、脅威検知と自動対応の高度化
参考

公式ドキュメントのBlueprint（docs.cyberark.com の「CyberArk Blueprint」）では、侵入後の攻撃に対する3つの原則として「アイデンティティ侵害（資格情報窃取）の防止」「横方向・縦方向の移動の阻止」「権限昇格と悪用の制限」を挙げており、上表はこれを新人向けに要約したものです（2026-10-19確認）。各原則に対応する具体的な統制（Vault格納・ローテーション・分離、JIT・一意のローカル資格情報、最小権限・ZSP・脅威検知など）は同ドキュメントを参照してください。

最初の成果（クイックウィン）を早く出す

導入プロジェクトは長期化しがちです。「ドメイン管理者を全部Vaultに入れ、パスワードを自動変更した」のような経営層にも伝わる最初の成果を早めに作ると、その後の展開がスムーズになります。

5. 障害対応の型

🔎

①影響範囲（1人？全員？）→ ②どの矢印か（第3章の図）→ ③最近の変更 → ④ログ → ⑤ナレッジ検索 → ⑥サポートへエスカレーション

「全員が使えない」なら共通部分（Vault・PSMサービス・証明書・内部アカウント・ネットワーク）、「1アカウントだけ」ならそのアカウントの設定・ターゲットを疑います。

サポートに問い合わせるときに揃えるもの
  • 製品・バージョン（Self-Hosted／Privilege Cloud、コンポーネントのバージョン）
  • 発生日時、影響範囲、再現手順、エラーメッセージ（画面キャプチャ）
  • 関連コンポーネントのログ（パスワード等の機密が含まれていないか確認してから提出）
  • 直前に行った変更

6. 自動化（REST API）

PVWA（Privilege CloudではそのAPI）はREST APIを提供しており、Safe作成・アカウント登録・権限付与などを自動化できます。サーバ構築の自動化（IaC）と連動して「構築したらすぐCyberArkに登録」を実現できます。

# 例：Self-Hosted PVWA の REST API（概念例。実際のエンドポイント・認証方式はバージョンの公式APIリファレンスで確認）
# 1) ログオン（トークン取得）
POST https://pam.hikari.example/PasswordVault/API/auth/CyberArk/Logon
# 2) アカウント登録
POST https://pam.hikari.example/PasswordVault/API/Accounts
{
  "safeName": "HK-PRD-INF-LNX-ROOT",
  "platformId": "HK-Unix-SSH-Root",
  "address": "hk-web03.hikari.example",
  "userName": "root",
  "secretType": "password",
  "secret": "（初期パスワード）"
}
自動化用の資格情報こそ守る

API用のユーザーは強い権限を持ちがちです。権限は必要最小限にし、その資格情報自体もCyberArk（CP/CCP等）から取得するようにします。PowerShell向けのコミュニティモジュール（psPAS）や、Ansibleの公式コレクションなども活用されています。

7. バージョンアップとサポート

  • Self-Hosted：サポート期間の区分（長期サポートのLTS、標準のSTS。LTSと明記されていない版はSTS）があります。公式のEnd of Life Policy（2026-10-19確認）では次のとおりです。
    バージョンリリース開発終了（修正提供の終了）サポート終了
    15.2（LTS）2026年7月2029年7月2029年7月（有償延長で2031年7月）
    15.0（STS）2025年12月2026年12月2027年12月
    14.6（LTS）2025年6月2028年6月2028年6月（有償延長で2030年6月）
    アップグレードはLTSから次のLTS、または最新版へのみサポートされ、LTSの修正を受けるには全コンポーネントを同じLTSにそろえる必要があります。15.2ではIdiraブランドへの名称変更も始まっています。
  • アップグレード順序：公式の互換性ページでは Vault → PVWA → CPM の順に上げ、その後に他のコンポーネント（PSM等）を上げるとされています（例：CPM 15.2 は Vault・PVWA が15.2以上であることが前提）。Primary-DR構成ではPrimary Vault → DR Vault → コンポーネントの順です。組み合わせによって条件が異なるため、作業前に必ず該当バージョンのアップグレードガイドと互換性表を確認します。
  • Privilege Cloud：SaaS側は自動で更新されます。コネクタ側のコンポーネント（CPM・PSM等）は、更新の仕組みと対応バージョンを確認して計画的に更新します。

振り返り問題（第15章）

Q1. 「PSMを通らずにサーバへ直接RDPできる経路が残っている」ことの問題は？

  • Vaultの暗号化が無効になる
  • 統制と検知を迂回する抜け道になり、記録も残らない
  • CPMのパスワード変更が速くなる
  • 特に問題はない
経路の一本化（原則5）ができていないと、PSMの録画・承認・PTAの検知がすべて迂回されます。

Q2. 段階導入で最初に取り組むべき対象として最も適切なのは？

  • 社員PCのブラウザ設定
  • 検証環境のテストアカウント
  • 利用頻度の低いアプリのログ
  • ドメイン管理者などの最重要アカウント
リスクが最も高い最重要アカウントから始めます。

Q3. オンボーディングで「依存先の調査」を怠ると起こりやすい問題は？

  • パスワード変更後にサービスやタスクが起動しなくなる
  • 録画が再生できなくなる
  • Masterユーザーがロックされる
  • Safe名が長くなる
依存先（サービス・タスク・設定ファイル）が更新されず、業務障害につながります。

Q4. Self-Hostedのバージョンアップ計画で必ず行うべきことは？

  • 全コンポーネントを同時に再インストールする
  • Vaultをドメインに参加させる
  • 公式のアップグレードガイドと互換性表で順序・互換性を確認する
  • バックアップを停止する
順序や互換性はバージョンの組み合わせで異なるため、公式ガイドの確認が必須です。
