CHAPTER 08｜設計・設定

CPMとパスワードライフサイクル

CPMは「定期的に鍵を作り替える錠前師」です。変更（Change）・検証（Verify）・調整（Reconcile）の3つの仕事と、失敗したときの調べ方を身につけます。

この章の全体像

CPMの3つの仕事 → 実行のきっかけ → 変更処理の内部フロー → 調整（Reconcile）のフロー → よくある失敗と切り分け → CPMの配置設計

この章のゴール

  • Change・Verify・Reconcileの違いを説明できる
  • パスワード変更時に「パスワードが失われない」仕組みを説明できる
  • CPMエラーの典型原因を挙げ、ログを見て切り分けを始められる
目安 90分前提：第7章重点章

1. CPMの3つの仕事

マンションの鍵を管理する錠前師

変更（Change）：定期的に鍵穴ごと新しい鍵に取り替える。
検証（Verify）：管理室にある鍵で、本当にドアが開くか試してみる。
調整（Reconcile）：誰かが勝手に鍵を替えてしまい管理室の鍵で開かないとき、管理会社のマスター権限で鍵を強制的に作り直す。

操作何をする使う権限主なきっかけ
Change新しいパスワードを生成し、ターゲットとVaultの両方を更新対象アカウント自身（またはLogon Account経由）定期変更、手動実行、利用後（ワンタイム）
VerifyVaultのパスワードで実際にログインできるか確認対象アカウント自身定期検証、手動実行、登録時
Reconcile不一致のパスワードを、高権限アカウントで強制リセットReconcile Account検証失敗時（自動設定時）、手動実行
🔁

Verifyで「ズレ」に気づき、Reconcileで「ズレ」を直し、Changeで「漏れても使えない」状態を保つ。

定期変更・定期検証の間隔はMaster Policyとプラットフォームで決めます（例：変更90日ごと、検証7日ごと。値は組織の規程に合わせる）。

2. 変更処理の内部フロー

パスワード変更で一番怖いのは「ターゲットだけ新しいパスワードに変わったのに、Vaultに保存できず、誰も新しいパスワードを知らない」状態です。CPMはこれを避けるため、先にVaultへ新パスワードを控えてからターゲットを変更します。

3. 調整（Reconcile）のフロー

誰かがCyberArkを通さずにパスワードを変えた、OSを再構築した、バックアップから戻した——こうした理由でVaultとターゲットのパスワードがズレることがあります。

4. よくある失敗と切り分け

症状・エラーの傾向よくある原因確認すること
接続できない・タイムアウトFW遮断、DNS解決不可、ターゲット停止CPMサーバからの疎通（ポート）・名前解決
認証失敗（Verify失敗）パスワード不一致、アカウントロック・失効ターゲット側のロック状態、直接変更の有無 → Reconcile
変更が拒否されるパスワードポリシー不一致（長さ・記号・履歴・最小有効期間）ターゲットのポリシーとプラットフォーム設定を照合
権限不足Logon/Reconcile Accountの権限不足、sudo設定不足連携アカウントの権限・sudoers
Unix系で途中停止プロンプト文字列の不一致（言語設定、独自のログインバナー等）プラグインの詳細ログ、プロンプト設定
変更されない（処理されない）CPMがSafeに割り当てられていない、時間帯制限、自動管理が無効Safeの担当CPM、プラットフォームの実行時間帯、アカウントの状態
ログの見方（Self-Hostedの例）

CPMサーバのログフォルダ（既定 C:\Program Files (x86)\CyberArk\Password Manager\Logs）には、すべてのメッセージを含む pm.log と、警告・エラーだけの pm_error.log があり（公式「CPM logs」で確認）、プラグインの詳細ログはデバッグを有効にしたときに出力されます。まずPVWA上のエラーメッセージでどの段階（接続・ログオン・変更・検証）で失敗したかを掴み、次にログで詳細を確認します。デバッグは調査後に必ず無効へ戻しましょう（ログ肥大化と情報露出の防止）。

連続失敗はアカウントロックを招く

パスワード不一致のまま検証を繰り返すと、ターゲット側のロックアウトポリシーでアカウントがロックされることがあります。特にドメインアカウントでは業務影響が大きいので、エラーが続く場合は早めに自動管理を一時停止し、原因を調べます。

5. CPMの配置設計

  • Safeごとに担当CPMを1つ割り当てる：アカウントが多い場合や、ネットワークが分かれている場合はCPMを複数台にして担当Safeを分けます。
  • ターゲットに到達できる場所に置く：拠点やクラウドごとにCPMを置くことで、FW越えを最小化します（Privilege Cloudではコネクタとして配置）。
  • 処理の集中を避ける：一斉に変更日を迎えないよう、登録時期を分散させる・時間帯を設定するなどの工夫をします。

Self-Hosted と Privilege Cloud の違い（この章のポイント）

🏢 Self-Hosted の場合

  • CPMサーバ（Windows）を自社で構築し、Safeごとに担当CPMを割り当てる
  • ログは CPM の Logs フォルダ（pm.log／pm_error.log）

☁ Privilege Cloud の場合

  • 推奨は Secrets Rotation Service（SRS）：SaaS上でアクティブ-アクティブ構成・自動スケールするローテーションエンジン。変更処理はコネクタの Connector Management エージェント経由でターゲットに対して実行
  • エージェントはコネクタプール単位で冗長化（1プールに2エージェント）
  • SRSの制限：Credential Providerの dual account 管理や、管理者が自分専用の特権アカウントを作る機能に未対応、一部AWSリージョン非対応 など
  • 従来どおりコネクタにCPMを置く構成も選択可能。CPMからSRSへの移行時は動作の違い（behavior changes）を確認

出典（2026-10-19確認）：Deploy Privilege Cloud Connector、Secrets Rotation Service architecture、Secrets Rotation limitations、CPM logs

振り返り問題（第8章）

Q1. Vaultのパスワードとターゲットのパスワードが食い違ったときに、高権限アカウントで強制リセットする操作は？

  • Verify
  • Reconcile
  • Change
  • Retrieve
Reconcile（調整）です。Reconcile Accountの権限を使います。

Q2. CPMがターゲットを変更する前に新パスワードをVaultへ控える理由は？

  • 変更処理を高速化するため
  • 録画を開始するため
  • 途中で失敗しても新パスワードが失われないようにするため
  • 利用者にメール通知するため
ターゲットだけ変わってVaultに残らない事故を防ぐための仕組みです。

Q3. 「パスワード変更は成功するのに、Unixの一部サーバだけ途中で止まる」。最初に疑う点として適切なのは？

  • プロンプト文字列（言語設定やログインバナー）の不一致
  • Vaultのディスク容量
  • PVWAの証明書期限
  • Masterユーザーのパスワード
Unix系プラグインは画面のプロンプトを見て対話するため、言語設定やバナーの違いで止まることがあります。

Q4. 検証失敗が続くドメインアカウントへの対応として最も適切なのは？

  • そのまま放置して自動で直るのを待つ
  • 検証間隔を1分にする
  • Safeを削除する
  • ロックアウトの危険があるため自動管理を一時停止し、原因を調べる
繰り返しの失敗ログオンはロックアウトを招きます。一時停止して原因を特定します。
