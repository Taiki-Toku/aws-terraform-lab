CHAPTER 04｜コア構成

Digital Vaultとセキュリティ

Vaultは「会社中のマスターキーが入った金庫」です。金庫そのものが破られたら終わりなので、Vaultは他のサーバとはまったく違う考え方で守られます。

この章の全体像

Vaultの設計原則（専用・堅牢化・非ドメイン）→ 多層防御と暗号化 → 組み込みユーザーと緊急用Master → 可用性（DR・バックアップ）→ フェイルオーバーの流れ

この章のゴール

  • Vaultを「ドメインに参加させない」「他のソフトを入れない」理由を説明できる
  • Masterユーザー・Administratorユーザー・Auditors等の組み込みユーザー／グループの違いを説明できる
  • DR Vaultへの切り替えの流れと、コンポーネント側の動きを説明できる
目安 70分前提：第3章

1. Vaultの設計原則

銀行の地下金庫は「普通の部屋」ではない

銀行の金庫室は、窓がなく、入口は1つだけ、壁は分厚く、清掃業者も自由には入れません。Vaultサーバも同じで、入口（通信ポート）は原則1つ、余計なもの（他のソフトウェア・ドメイン参加）は置かないのが基本です。

原則内容理由
専用サーバVaultサーバには他の役割（ファイルサーバ、監視エージェント等）を同居させない他ソフトの脆弱性が攻撃の入口になる（攻撃対象領域の拡大）
ドメイン非参加Active Directoryドメインに参加させない（ワークグループ）ドメインが侵害されても、ドメイン管理者がVaultサーバに入れないようにする
堅牢化（ハードニング）インストール時に不要なサービス停止・OS設定の強化が自動で行われる攻撃に使える機能を最初から取り除く
専用ファイアウォールVaultがWindowsファイアウォールを制御し、既定ではVaultプロトコル（TCP 1858）のみ受け付ける入口を1つに絞り、不要な通信を遮断する
物理的・論理的なアクセス制限コンソールアクセスできる人を最小限にし、仮想環境ならハイパーバイザ管理者も統制するOSより下のレイヤ（物理・仮想基盤）からの攻撃を防ぐ
よくある失敗
  • 「監視のために」Vaultサーバに汎用の監視エージェントやリモート管理ツールを入れてしまう
  • 「管理が楽だから」Vaultをドメインに参加させてしまう
  • FWの例外を増やし、RDPを常時開放してしまう

いずれも金庫室に裏口を作る行為です。必要な場合は公式のガイドに沿って、例外を最小限にします。公式GitHubの CYBRHardeningCheck のように、堅牢化状態（ドメイン非参加かどうか等）を確認するツールも提供されています。

2. 多層防御と暗号化

Vaultは、1つの対策が破られても次の対策で守る多層防御の考え方で設計されています。

🔒 通信の暗号化

コンポーネントとVault間の通信は暗号化される。

🧱 ファイアウォール

Vault自身がFWを管理し、許可された通信のみ受け付ける。

🪪 認証

パスワード、LDAP、RADIUS、PKI、SAMLなど多様な認証方式と多要素認証。

🗝 アクセス制御

Safe単位の細かい権限。Vault管理者であっても権限がなければ中身は見えない設計が可能。

📜 監査

すべての操作を改ざん困難な形で記録。

🔐 保存データの暗号化

格納データは階層的な鍵で暗号化して保存。

階層的な暗号化（鍵の入れ子）

Vaultに保存されるファイルは、ファイルごとの鍵で暗号化され、その鍵はSafeの鍵で、Safeの鍵はVaultのServer Keyで暗号化されます。

マトリョーシカ型の鍵束

書類（データ）は鍵付きの封筒（File Key）に入り、その封筒の鍵はさらに部屋ごとの金庫（Safe Key）に、部屋の金庫の鍵は建物全体の親鍵（Server Key）で守られています。Vaultのディスクだけを盗まれても、親鍵がなければ中身は読めません。

Server Keyのほかにリカバリキー（Recovery Key）があります。リカバリキーの秘密鍵は一般に「Master CD」と呼ばれる媒体に格納され、Vaultサーバとは別の場所（オフライン）で厳重に保管します。Masterユーザーでのログインや緊急時の復旧に使われます。

3. 組み込みユーザーとグループ

Vaultはインストール時に、いくつかのユーザーとグループを自動作成します。代表的なものを覚えましょう。

名前種類特徴運用上の扱い
Masterユーザー「Authorize password requests（承認）」を除くすべてのSafe権限を持ち、どのSafeからも削除できない。System Safeを編集できる唯一のユーザー。ログインはPrivate Recovery Keyを含むMaster CDでのみ可能緊急時専用（ブレークグラス）。普段は絶対に使わない
Administratorユーザー初期の管理者ユーザー。Masterと違い、新しいSafeへ自動で全権限が付くわけではない初期構築後は厳重保管し、日常は個人名の管理者アカウントを使う
Vault AdminsグループVaultの管理機能（PVWAの管理画面等）を使える管理者グループメンバーは最小限に。LDAPグループをマッピングすることが多い
AuditorsグループView audit と View Safe Members 権限を持ち、Safeの内容・操作ログ・オーナー一覧を参照できる（組み込みのAuditorユーザーが所属）監査担当・内部監査部門
Backup Users / DR Users / Operators などグループ・ユーザーBackup Users・DR UsersはBackup Safe権限（バックアップ・DR複製用）、OperatorsはManage Safe権限（Safeのプロパティ変更等。中身は見えない）用途専用。対話ログインには使わない
🚨

Masterユーザーは「非常口の鍵」。使ったら必ず事後報告・記録・原因対策。

Masterの利用は、全管理者がロックアウトされた等の非常事態に限ります。利用手順（誰が立ち会い、どこから鍵を出し、どう記録するか）を事前に文書化しておくのが設計者の仕事です。

公式ドキュメントで確認済み（2026-10-19）

出典：PAM - Self-Hosted「Predefined users and groups」。なお、Master以外の組み込みユーザーは作成時点では無効（disabled）で、使うには有効化が必要です。組み込みユーザー・グループを自動追加されたSafeから外せるかどうかは、DBParm.ini の設定で決まります。

4. 可用性：DR・バックアップ・冗長化

Vaultが止まるとPAM全体が止まり、特権作業ができなくなります。そのため可用性設計は必須です。

方式概要守れるもの
DR Vault別サイトに待機用Vaultを置き、DRサービスがデータを継続的に複製。本番障害時にDR Vaultを起動して切り替えるサイト障害・サーバ障害
クラスタ構成同一サイト内で2台のVaultを共有ストレージ等で冗長化（Cluster Vault）サーバ単体の障害（同一サイト内）
バックアップ専用のバックアップユーティリティ（PAReplicate等）でVaultデータを取得し、外部のバックアップ製品で保管論理障害・誤操作・ランサムウェア（世代管理）
コンポーネント冗長化PVWA・PSMは複数台＋ロードバランサ、CPMは担当範囲を分けて複数台コンポーネント障害・性能
DRとバックアップは別物

DRは「最新の状態をすぐに引き継ぐ」仕組みなので、誤って削除したデータもそのまま複製されます。過去の状態に戻すにはバックアップが必要です。両方を設計しましょう。

DR訓練は「やってみないと分からない」

FWでDRサイトへの1858が開いていない、DR側PSMの録画保存先が足りない、手順書が古い…といった問題は、訓練で初めて見つかることがほとんどです。

Self-Hosted と Privilege Cloud の違い（この章のポイント）

🏢 Self-Hosted の場合

  • Vaultの堅牢化・パッチ・鍵（Server Key／Master CD）・DR・バックアップはすべて自社の責任
  • 組み込みユーザー（Master・Administrator 等）とグループ（Vault Admins・Auditors 等）を自社で管理

☁ Privilege Cloud の場合

  • Vaultの運用・堅牢化・DR・バックアップはサービス提供側の責任範囲
  • 顧客が守るのは、管理者の役割（Privilege Cloud Administrators／Auditors／Safe Managers）、認証基盤（Identity）、コネクタサーバの堅牢化（提供されるGPO堅牢化パッケージ）
  • 組み込みユーザーは編集・削除できず、アプリ用の組み込みユーザーはライセンスを消費しない
  • IdP障害などに備えた緊急時のログイン手順は、SaaSでも顧客側で用意する

出典（2026-10-19確認）：Predefined users and groups、Privilege Cloud built-in users、ISPSS user roles、Upgrade connector components

振り返り問題（第4章）

Q1. VaultサーバをActive Directoryドメインに参加させない主な理由は？

  • ライセンスがドメイン参加を禁止しているから
  • ドメインが侵害されても、ドメイン管理者権限でVaultサーバへ侵入されないようにするため
  • ドメイン参加するとTCP 1858が使えなくなるから
  • ドメイン参加するとバックアップが取れないから
ドメイン侵害がVault侵害に直結しないよう、Vaultは独立させます。

Q2. Masterユーザーの説明として正しいものは？

  • 日常の管理作業で使う標準的な管理者
  • 監査ログを閲覧するためだけのユーザー
  • PVWAのREST API専用ユーザー
  • どのSafeからも削除できず（承認権限を除く）全権限を持ち、Master CDのリカバリキーでのみログインできる緊急用ユーザー
Masterは緊急時専用です。日常使用は厳禁です。

Q3. 「誤って削除したアカウント情報を前日の状態に戻したい」場合に必要なのは？

  • バックアップ
  • DR Vault
  • PSMの冗長化
  • ロードバランサ
DRは最新状態を複製するため削除も複製されます。過去の状態への復元にはバックアップが必要です。

Q4. Vaultの保存データ暗号化の鍵階層で、最上位にあるのは？

  • File Key
  • Safe Key
  • Server Key
  • 利用者のパスワード
Server Key → Safe Key → File Key → データ の順に入れ子で暗号化されます。
