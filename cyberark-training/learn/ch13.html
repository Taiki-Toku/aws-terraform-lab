CHAPTER 13｜発展

アプリケーションとシークレット管理

人ではなく「プログラム」が使うパスワードやAPIキー（シークレット）をどう守るか。設定ファイルへのパスワード直書きをなくすための仕組みを学びます。

この章の全体像

ハードコードの問題 → 「シークレット・ゼロ」問題 → Credential Provider（CP）と Central Credential Provider（CCP）→ CCPでの取得フロー → Secrets Manager（旧Conjur）→ Secrets Hub → 使い分け

この章のゴール

  • アプリのパスワード直書きのリスクと、「シークレット・ゼロ」問題を説明できる
  • CPとCCPの違い、アプリ認証（Application ID）の仕組みを説明できる
  • CP/CCP・Secrets Manager・Secrets Hubを、アプリの種類に応じて使い分けられる
目安 75分前提：第6〜8章

1. ハードコードの問題

開発チームの中村さんのアプリは、設定ファイルに次のように書かれていました（架空の例）。

# /opt/hk-sales/config/db.properties
db.url=jdbc:oracle:thin:@hk-db01.hikari.example:1521/SALES
db.user=appuser
db.password=Hikari2019!   ← 平文のまま、7年間変更なし
直書き（ハードコード）が危険な理由
  • サーバに入れた人・ソースコードを見た人なら誰でもパスワードを知ることができる
  • Git等のリポジトリやバックアップ、チャットに貼られて拡散する
  • 変更するとアプリが止まるため、何年も変更されない
  • 同じパスワードが複数環境で使い回されがち

「シークレット・ゼロ」問題

金庫の鍵を、どこにしまうか

「パスワードは金庫（Vault）に入れました。アプリは金庫から取り出します」——では、アプリが金庫を開けるための鍵はどこに置くのでしょうか？それを設定ファイルに書いたら元の木阿弥です。この「最初の1つの秘密」をどう扱うかがシークレット・ゼロ問題です。CyberArkは、パスワードの代わりに「アプリ自身の属性」（どのマシンで、どのOSユーザーで、どのプログラムが動いているか、証明書、クラウドやKubernetesが発行するID）で本人確認することで、この問題を解決します。

2. Credential Provider（CP）とCentral Credential Provider（CCP）

項目CP（Credential Provider）CCP（Central Credential Provider）
形態アプリサーバにエージェントを導入エージェント不要。中央のWebサービスにREST等で問い合わせ
可用性ローカルキャッシュを持ち、Vaultに一時的に接続できなくても取得可能CCPサーバの冗長化（複数台＋ロードバランサ）で確保
アプリ認証OSユーザー、実行パス、ハッシュ、許可マシン等許可マシン（送信元IP）、クライアント証明書等
向いている場面エージェントを入れられるサーバ、高い可用性が必要エージェントを入れられない機器・アプライアンス・外部製品との連携（RPA等）

アプリケーションサーバのデータソース（接続プール）向けに、アプリのコードを変えずに資格情報を提供する仕組み（ASCP）もあります。

アプリをVaultに登録する（Application ID）

  1. PVWAでアプリケーションを登録し、Application ID（例：HK-SalesApp）を決める
  2. アプリ認証の条件を設定する（許可マシン 10.30.1.21、クライアント証明書、OSユーザー等）
  3. アプリ用Safe（HK-PRD-APP-ORA-APPUSR）に、アプリ（Application ID）と、CP/CCPのProviderをメンバーとして追加する（主にList accounts と Retrieve accounts。Providerにはさらに View Safe members 等が必要）
  4. 人のメンバーにはRetrieveを付けない（人は見られない設計にする）

4. Secrets Manager（旧 Conjur）

コンテナ、Kubernetes、CI/CDパイプラインなど、短時間で大量に生まれては消えるワークロード向けのシークレット管理です。SaaS版とSelf-Hosted版があります。

  • ポリシー・アズ・コード：誰（どのワークロード）がどのシークレットを使えるかを、コード（YAML等）で定義・レビューできる
  • プラットフォームのIDで認証：Kubernetesのサービスアカウント、クラウドのIAMロール、JWTなどを使い、シークレット・ゼロ問題を解消
  • PAMとの同期：VaultのSafeに入っているアカウントを同期して、CPMによる自動変更の恩恵を受けられる構成がある

5. Secrets Hub

本社の金庫と各支店の金庫

AWS Secrets ManagerやAzure Key Vaultは「各クラウドに備え付けの金庫（支店の金庫）」です。開発者は使い慣れたその金庫を使いたい。一方セキュリティ部門は、ローテーションや監査を本社（CyberArk）で一元管理したい。Secrets Hubは、本社金庫の中身を支店金庫に自動で配送・同期する仕組みです。

  • CyberArk（Privilege Cloud／Self-Hosted）で管理・ローテーションしたシークレットを、AWS Secrets Manager・Azure Key Vault・GCP Secret Manager・HashiCorp Vaultへ同期（公式「Secrets Hub support and scope」2026-10-19確認。鍵・証明書は対象外）
  • 各クラウドとの信頼関係は、AWSはIAMロール、AzureはApp Registration（新規はフェデレーションIDのみ）、GCPはサービスアカウント／Workload Identity Federationで構成
  • アプリはクラウドの標準APIのまま使えるため、アプリ改修が少ない
  • クラウドのシークレットストアにある既存シークレットを発見・可視化し、CyberArkの管理下へ取り込む機能も拡充されている（2025年のアップデート）

6. 使い分け

アプリの種類第一候補理由
オンプレの従来型業務アプリ（エージェント導入可）CPローカルキャッシュで高可用
アプライアンス・パッケージ製品・RPACCPエージェント不要、製品側の連携機能が対応していることが多い
Kubernetes・コンテナ・CI/CDSecrets ManagerワークロードIDで認証、ポリシー・アズ・コード
クラウドネイティブアプリ（AWS/Azure等の標準ストアを利用）Secrets Hubアプリ改修を最小にしつつ一元管理

Self-Hosted と Privilege Cloud の違い（この章のポイント）

🏢 Self-Hosted の場合

  • CP／CCPは自社のVaultに接続
  • Secrets HubはSelf-HostedのPAMをソースとして利用可能

☁ Privilege Cloud の場合

  • CP／CCPはPrivilege Cloudでも利用可能（アプリ認証・Safe権限の考え方は同じ）
  • Secrets HubはPrivilege Cloudをソースとして利用可能
  • パスワード変更をSecrets Rotation Serviceで行う場合、Credential Providerの dual account 管理は未対応（設計時に注意）

出典（2026-10-19確認）：Secrets Hub support and scope、Secrets Rotation limitations

振り返り問題（第13章）

Q1. 「シークレット・ゼロ問題」の説明として正しいものは？

  • Vaultにパスワードが1件もない状態
  • アプリが金庫を開けるための「最初の秘密」をどこに置くかという問題
  • パスワードの長さが0文字になる不具合
  • CPMが停止している状態
CyberArkはパスワードの代わりにアプリの属性やプラットフォームIDで認証して解決します。

Q2. エージェントを導入できないアプライアンスからパスワードを取得させたい。適切なのは？

  • CCP
  • CP
  • PSM for SSH
  • EPM
CCPはエージェント不要のWebサービス型です。

Q3. CPの特徴として正しいものは？

  • エージェント不要
  • 人のRDP接続を録画する
  • クラウドのシークレットストアと同期する
  • ローカルキャッシュを持ち、Vaultに一時的に接続できなくても取得できる
CPはエージェント型でローカルキャッシュを持つため可用性が高いのが特徴です。

Q4. AWS Secrets Managerを使うアプリを改修せずに、ローテーションと監査をCyberArkで一元管理したい。適切なのは？

  • PSM
  • EPM
  • Secrets Hub
  • PrivateArk Client
Secrets HubはCyberArkで管理したシークレットをクラウドのストアへ同期します。
