CHAPTER 06｜設計・設定

Safe設計と権限モデル

Safeの切り方は、あとから変えるのが大変な「家の間取り」です。権限は「誰がその部屋に入れて、何ができるか」。ここがCyberArk設計の中心です。

この章の全体像

Safeとは → Safe設計の考え方と命名規則 → Safeメンバーと権限一覧 → 「Use」と「Retrieve」の違い → 権限チェックの流れ

この章のゴール

  • 組織・システム・環境の観点で、Safeの分割案を作れる
  • 主要なSafe権限（List / Use / Retrieve / 承認 等）の意味を説明できる
  • 「パスワードを見せずに接続だけさせる」権限設定ができる
目安 90分前提：第3章重点章

1. Safeとは

Safeは、アカウント（特権IDの資格情報）をまとめて入れておく箱であり、アクセス権を付与する単位です。

銀行の貸金庫の「箱」

銀行の金庫室（Vault）の中には、たくさんの貸金庫の箱（Safe）が並んでいます。箱ごとに「開けられる人の名簿（Safe Member）」があり、名簿にない人は、たとえ銀行員（Vault管理者）でも勝手に中を見られないようにできます。権限は「アカウント1件ずつ」ではなく「箱ごと」に付けるのがポイントです。

📦

同じ人たちが、同じ使い方をするアカウントを、同じSafeに入れる。

権限がSafe単位で付くため、「使う人」と「使い方」がそろっているかがSafe分割の判断基準になります。

2. Safe設計の考え方

分割の観点

観点例分ける理由
管理する組織・チームインフラ課／DB課／ネットワーク課使う人が違う
環境本番（PRD）／検証（STG）／開発（DEV）本番だけ承認や録画を厳しくしたい
ターゲット種別Windows／Linux／DB／NW機器担当CPM・ポリシーが異なることが多い
重要度ドメイン管理者などの最重要アカウント最小人数・二重承認など特別扱い
利用者種別人が使う／アプリが使う（第13章）アプリ用は人に見せない権限設計
外部委託保守ベンダー用契約単位で付与・剥奪したい

命名規則の例（ヒカリ精機）

[会社]-[環境]-[組織]-[種別]-[用途]
例) HK-PRD-INF-LNX-ROOT   … 本番 インフラ課 Linux rootアカウント
    HK-PRD-DBA-ORA-SYS    … 本番 DB課 Oracle 管理者
    HK-STG-INF-WIN-LOCAL  … 検証 インフラ課 Windowsローカル管理者
    HK-PRD-APP-ORA-APPUSR … 本番 アプリ用 Oracle 接続ユーザー（第13章）
    HK-PRD-VND-NEXT-WIN   … 本番 委託先（ネクスト保守）用 Windows
Safe名には制約がある

公式ドキュメントでは、Safe名は最大28文字で、\ / : * < > . | ? " % & + などの文字は使えません（Privilege Cloudでは ; も不可）。Secrets Hubでクラウドへ同期する場合は、Azure Key Vault（英数字とハイフンのみ）など同期先の命名制約も受けます。またSafe名は後から変えにくい（連携設定・スクリプト・レポートが名前に依存する）ため、命名規則は導入初期に決めて文書化しましょう。

ちょうどよい粒度

「全部1つのSafe」は権限が粗すぎ、「サーバ1台に1Safe」は管理不能になります。「権限付与の単位がそろう最大のまとまり」を目安にしましょう。

Safeのその他の主な設定

  • 担当CPM：そのSafe内のアカウントのパスワード管理をどのCPMが担当するか（第8章）
  • 保持設定：過去のパスワード版や操作履歴をどれだけ保持するか（世代数または日数）
  • 説明・オーナー情報：Safeの責任者を明記（棚卸しで必須）

3. Safeメンバーと権限

Safeメンバーには、Vaultユーザー、LDAP（AD）ユーザー、グループを追加できます。個人ではなくADグループを登録しておけば、異動・退職時はADのグループ変更だけで済みます。

主な権限一覧

分類権限（英語表記）できること
アカウントの利用List accountsSafe内のアカウント一覧を見る（他の操作の前提）
Use accountsパスワードを見ずにアカウントを使う（PSM経由の接続など）
Retrieve accountsパスワードを表示・コピーする
アカウントの管理Add accountsアカウントを登録する
Update account contentパスワード等の値を更新する
Update account propertiesアドレス・ユーザー名等の属性を更新する
Initiate CPM account management operationsCPMの変更・検証・調整を手動で実行する
Specify next account content次回CPMが設定するパスワードを指定する
Rename / Delete / Unlock accounts名前変更・削除・ロック解除
Safeの管理Manage SafeSafeのプロパティ変更
Manage Safe membersメンバーの追加・削除・権限変更
Backup SafeSafeのバックアップ
Create / Delete folders、Move accounts and foldersフォルダ操作
監査View audit logSafeの操作ログを見る
View Safe membersメンバー一覧を見る
ワークフローAuthorize account requests（レベル1／2）アクセス申請を承認する（第9章）
Access Safe without confirmation二重承認が必要なSafeでも承認なしで使える（緊急要員等。付与は慎重に）

「Use」と「Retrieve」の違い（最重要）

✅ List ＋ Use

PSM経由で接続はできるが、パスワードは見えない。
→ 一般の運用担当・委託先に推奨。パスワードを知る人が増えないので、変更頻度を下げても安全性を保ちやすい。

⚠ List ＋ Retrieve

パスワードを表示・コピーできる。
→ PSMで対応できない機器や緊急時など、必要な人に限定。見た後はワンタイムパスワード等で変更する運用と組み合わせる。

迷ったら「Use」

「パスワードを見せない」ことがCyberArkの最大の価値の1つです。Retrieveは理由がある人にだけ付けます。

役割ごとの権限セット例

PVWA・Privilege Cloudの画面では、よく使う組み合わせがプリセット（例：接続のみ、閲覧、承認者、アカウント管理者、フル）として用意されています。名称はバージョンにより異なります。

役割（ADグループ例）主な権限
運用担当（GG_PAM_INF_USERS）List, Use
上級運用担当（GG_PAM_INF_ADV）List, Use, Retrieve
承認者（GG_PAM_INF_APPROVERS）List, Authorize account requests
アカウント管理者（GG_PAM_INF_ACCTMGR）List, Add, Update content/properties, Initiate CPM operations, Delete
Safe管理者（GG_PAM_ADMINS）Manage Safe, Manage Safe members, View audit, View members（※日常的なアカウント利用権限は付けない）
監査担当（GG_PAM_AUDITORS）List, View audit log, View Safe members
職務分掌（SoD）を崩さない

「Safeのメンバーを管理できる人」が「自分にRetrieveを付けて使う」ことができると、統制が骨抜きになります。管理する人と使う人を分ける、自分自身への権限付与を監査ログで監視する、などの対策を組み合わせます。

4. 権限チェックの流れ

振り返り問題（第6章）

Q1. 委託先に「PSM経由で接続はさせたいが、パスワードは見せたくない」。付与すべき権限の組み合わせは？

  • List ＋ Retrieve
  • List ＋ Use
  • Manage Safe ＋ Retrieve
  • View audit log のみ
Useはパスワードを見せずに使わせる権限です。Retrieveは表示・コピーできてしまいます。

Q2. Safeメンバーとして、個人ではなくADグループを登録する主な利点は？

  • Vaultのライセンス数が減る
  • パスワード変更が速くなる
  • 録画容量が減る
  • 異動・退職時にADのグループ変更だけで権限が追随する
人事異動に伴う権限変更をAD側で一元管理でき、付け忘れ・外し忘れを防げます。

Q3. Safe分割の判断基準として最も適切なのは？

  • 同じ人たちが、同じ使い方をするアカウントをまとめる
  • サーバ1台につき1つのSafeを作る
  • 全アカウントを1つのSafeにまとめる
  • アカウントの登録日でまとめる
権限がSafe単位で付くため、利用者と使い方がそろう単位でまとめます。

Q4. 二重承認が必要なSafeでも、承認なしで使えるようにする権限は？

  • Authorize account requests
  • View Safe members
  • Access Safe without confirmation
  • Backup Safe
Access Safe without confirmationです。緊急対応要員などに限定して慎重に付与します。
